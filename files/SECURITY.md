# Security

## Auth Model

IconicSkies uses password-based authentication with server-managed sessions. Password login remains the default path. Email OTP can be used for verification and, when enabled for a user, as a second step after a correct password.

## Redis-Backed Email OTP

Email OTP challenges are stored only in Redis. PostgreSQL does not store OTP codes.

- OTP codes are numeric and short-lived
- challenges expire after `OTP_TTL_SECONDS` and default to 240 seconds
- resend cooldown defaults to 60 seconds
- verification attempts are capped and tracked per challenge
- successful verification consumes the challenge
- request and verify responses are intentionally generic to reduce account enumeration risk

## OTP Security Rules

- OTP codes are never stored in plaintext
- OTP codes are HMAC-hashed with `OTP_SECRET` or `AUTH_SECRET`
- Redis keys use hashed identifiers rather than raw email addresses
- OTP logging should remain disabled in production
- `OTP_DEV_LOG_CODES=true` is development-only and should not be enabled in deployed environments

SMS/mobile OTP is not a current production feature. Future SMS support should follow the same Redis-backed validation model and must not weaken the current email-first behavior.

## Password and Session Security

- Passwords are hashed server-side before storage
- sessions use secure, server-controlled cookies
- session records are scoped to the authenticated user
- protected routes and private resources enforce ownership checks before returning data

## API Keys and Secrets

All secrets stay server-side.

- `AUTH_SECRET`
- `OTP_SECRET`
- `OPENWEATHER_API_KEY`
- `GROQ_API_KEY`
- `GCS_PROJECT_ID`
- `GCS_CLIENT_EMAIL`
- `GCS_PRIVATE_KEY`
- `UPSTASH_REDIS_REST_TOKEN`
- email provider credentials

No secret should be exposed through `NEXT_PUBLIC_*` variables unless it is explicitly safe for the browser.

## Private GCS Photo Handling

Sky photos are uploaded through signed URLs generated by the server. The bucket remains private.

- object creation is scoped to the signed-in user
- upload completion validates ownership and expected object prefix
- private photos are not served directly from public bucket URLs

## Authenticated Media Route

Private image access goes through `/api/photos/[id]`.

- the route verifies the current session
- the route checks that the requested photo belongs to the signed-in user
- the server reads from GCS and streams the response back to the browser

This avoids exposing object paths or making the bucket public.

## Redis Caching and Rate Limiting

Redis is used only for derived or short-lived data:

- OTP challenges
- weather cache entries
- monthly recap cache entries
- AI route throttling

Redis is not the system of record for users, journal entries, sessions, or photos. PostgreSQL remains the durable source of truth.

Rate limiting is used to reduce abuse on AI and auth-related routes. Cache keys and throttling keys should avoid raw emails, raw tokens, private object paths, and full GPS precision.

## AI Privacy Rules

AI features are server-side and minimal by design.

- journal enhancement, title suggestions, and monthly recap use Groq from the server only
- requests send minimal journal and weather context
- private media URLs, GCS object paths, user emails, and secrets are never sent to the AI provider
- AI output is assistive and on-demand, not automatic background processing

## Historical Weather and Privacy

Past Sky Moments can be backdated up to 14 days. Historical weather is fetched using the validated captured time and selected captured city.

- the app does not silently substitute current weather for a past moment
- captured location is user-selected, not inferred from private photo metadata
- cached historical weather keys should use rounded coordinates rather than full-precision values

## Abuse Prevention

- input validation is enforced on auth, AI, upload, favorite, and Sky Moment routes
- protected resources require authentication and ownership checks
- OTP and AI routes are rate-limited
- production error responses should avoid leaking internal implementation details

## Production Environment Safety

- configure secrets only in a secure server-side environment such as Vercel project settings or a secret manager
- keep the GCS bucket private with public access prevention enabled
- rotate secrets if exposure is suspected
- do not commit real env values, test inboxes, OTP codes, or cloud credentials

## Logging Rules

- never log secrets in production
- never log OTP codes in production
- never log raw private photo paths or private media URLs
- keep diagnostic logging sanitized and scoped to what is needed to debug safely
